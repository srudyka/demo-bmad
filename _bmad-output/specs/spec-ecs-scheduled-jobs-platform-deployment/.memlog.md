updated: 2026-08-05T10:31

- (capability) CAP-1: Platform Engineering can deploy the account-local Platform Cell and one scheduled-job consumer into a real disposable non-production AWS environment. Success: the Cell root and job root create their owned resources in the approved Account/Region and the job schedule remains disabled until the Cell acknowledgement is accepted.
- (capability) CAP-2: An operator can deploy a configured ECS Fargate scheduled job using an immutable image and private networking. Success: one real occurrence launches through Scheduler → Cell → ECS, emits structured completion evidence, and exposes logs, alarms, retry, and DLQ results.
- (capability) CAP-3: The deployment can source non-secret target/configuration values from protected GitHub Environment configuration and sensitive values from an approved Infisical integration. Success: authorized workflow steps receive only scoped runtime secrets, while plans, state, artifacts, logs, and evidence contain no secret values.
- (capability) CAP-4: An authorized operator can run a protected deployment pipeline that validates, plans, approves, applies the exact saved plan, verifies the result, and publishes bounded evidence. Success: a changed target, plan, lock, role, source, or readiness binding fails before mutation, and a passing run records Deployment Identity and verification evidence.
- (capability) CAP-5: An authorized operator can run a separate protected destroy pipeline for the disposable non-production deployment. Success: only the approved disposable target is removed after confirmation, approval, and evidence preservation; production, shared Cell resources, protected state, retained evidence, and prevent-destroy resources are not removed.
- (capability) CAP-6: Platform and application operators can recover from failed or partial deployment, task execution, or teardown. Success: failures produce bounded diagnosis and recovery guidance, no mutation is retried automatically, and a subsequent mutation requires fresh target/plan/lock validation.
- (constraint) Use the account-local Cell-based architecture and preserve existing AD-1 through AD-34; shared Cell state is Platform Engineering-owned and job state is application-root-owned.
- (constraint) Use Terraform with committed provider locks, explicit validated interfaces, stable resource addresses, required ownership tags, encrypted state/data, private task networking, separate IAM roles, bounded retries, logs, alarms, DLQs, runbooks, and rollback notes.
- (constraint) Use immutable target binding, GitHub OIDC, protected GitHub Environments, separate plan/apply authority, exact saved-plan apply, full-SHA workflow/action references, and no long-lived AWS credentials.
- (constraint) GitHub Environment configuration is non-secret deployment control/configuration; Infisical uses OIDC-authenticated scoped machine identity for sensitive values. Secret values never enter Terraform variables/state/plans, CONFIG, artifacts, logs, or evidence.
- (constraint) The demonstration is non-production and disposable. Production activation, production destruction, arbitrary target selection, direct Scheduler-to-ECS bypass, terraform_remote_state, committed secrets/state/plans, mutable image tags, public task networking, and automatic broad cleanup are forbidden.
- (constraint) The deployment must preserve the publish → validate → materialize → enable handshake; missing Cell acknowledgement, readiness, target identity, secret retrieval, lock, or verification evidence fails closed.
- (constraint) All AWS resources must use least privilege, confused-deputy protections where supported, encryption at rest, explicit retention, operational tags, and no unjustified wildcard IAM or public exposure.
- (assumption) The initial target is one disposable non-production Account/Region with an approved Terraform backend, ECS cluster, ECR repository/image digest, private subnets/security groups, GitHub Environments, OIDC roles, Cell prerequisites, and Infisical project/machine identity.
- (assumption) Infisical is approved by Security and the Secret Owner for the selected project/environment/path scope and supports GitHub OIDC machine-identity authentication.
- (question) Which AWS Account, Region, backend, target manifest, GitHub Environment/reviewer set, OIDC subject, Infisical project/environment/path scope, and pilot job configuration will be used?
- (question) Which Cell resources must survive teardown, and which evidence/log retention policy applies before destroying the disposable consumer environment?
- (question) Will the first deployment use separate Cell and job Terraform roots with an explicit dependency, or a coordinated root that still preserves separate ownership and state?
