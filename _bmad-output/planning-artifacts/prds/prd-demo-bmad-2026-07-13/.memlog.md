topic: ECS Scheduled Jobs Platform Service
updated: 2026-08-05T09:56
---

- (decision) The product is an internal reusable platform capability that standardizes creation, deployment, monitoring, and operation of ECS scheduled jobs across AWS accounts and dev, staging, and prod environments.
- (decision) Primary users are platform, DevOps, SRE, and application engineers; security reviewers, engineering managers, on-call engineers, and cloud owners are secondary users.
- (decision) Version one includes a reusable Terraform module, ECS Fargate scheduling, least-privilege IAM, logs and actionable failure alarms, GitHub Actions delivery examples, tagging, examples, runbooks, rollback guidance, and production-readiness checks.
- (decision) Version one excludes a self-service UI, Kubernetes, complex orchestration and dependencies, enterprise scheduler replacement, secret lifecycle management, external approval systems, automatic remediation, cross-cloud support, and wholesale migration.
- (decision) Adoption must require little ECS expertise while keeping IAM permissions and important operational behavior explicit and reviewable.
- (decision) Production jobs require private networking, retained CloudWatch logs, actionable failure alarms, ownership tags, documented rollback, pull-request review, and approved production apply.
- (decision) Success means a team can define and deploy a reusable scheduled job across accounts without copy-paste drift, with least-privilege IAM, observable failures, ownership, rollback notes, and usable troubleshooting guidance.
- (decision) Fast path selected: remaining gaps will be batched, current practices researched, and the PRD drafted with explicit assumption tags for unresolved details.
- (decision) Platform Engineering or DevOps owns the module, workflow template, documentation, and standards; production approval requires Platform Engineering and the application owner, with Security review for qualifying IAM or networking changes.
- (assumption) Version one pilots one or two low-risk internal jobs within one sprint after MVP completion; exact jobs remain unknown.
- (assumption) After pilot acceptance all new ECS scheduled jobs use the standard, while existing jobs migrate when touched.
- (assumption) A basic job currently takes 1-3 days to set up; the target is under four hours and at least a 50 percent reduction.
- (decision) The platform creates task definitions, schedules, execution wiring, task roles and policies, log groups, alarms, tags, outputs, workflow examples, README, and runbook template; accounts, regions, networking, cluster, image, alert target, CI identity, and secret references are consumer inputs.
- (decision) Version one exposes schedule, time zone, retry, maximum-runtime expectation, overlap policy, manual-rerun guidance, and successful-completion contract; owners remain responsible for application idempotency or locking.
- (assumption) Production alarm destinations use an existing organizational alerting path supplied by consumers; the exact integration is unknown.
- (decision) Production governance blocks missing tags, unjustified IAM wildcards, public networking, missing logs or alarms, mutable images, plaintext secrets, and missing ownership metadata; non-production checks begin advisory.
- (assumption) Initial compatibility is Terraform 1.5 or newer, AWS provider 5.x or newer, GitHub OIDC, and Fargate platform LATEST, subject to implementation validation.
- (decision) The module uses semantic versioning, migration notes for breaking changes, and documented deprecation before removal.
- (assumption) Support covers the current major module version and one previous major version.
- (assumption) Until application owners are assigned, Platform Engineering or DevOps owns one or two low-risk pilot jobs; owners and exact jobs must be named before pilot execution.
- (assumption) Production alarm routing uses a consumer-supplied organization-standard incident target; Platform Engineering or DevOps on-call receives pilot alerts when no application support policy exists.
- (assumption) MVP completion detection uses a configurable success log pattern, CloudWatch Logs metric filter, and deadline alarm combined with ECS task status and exit-code signals; this must prove reliable in pilot testing.
- (decision) MVP maximum runtime is detection-only; enforced cancellation or an external watchdog is deferred.
- (assumption) The module is published from an internal GitHub repository, reusable workflows from a centralized platform repository, and consumers pin release tags; exact repository names remain unknown.
- (assumption) GitHub protected environments and required approval controls are available; equivalent auditable manual controls are required if they are not.
- (assumption) MVP validates one to five jobs in one non-production and one production account, in the organization standard primary Region, using one pilot application repository and the platform repository.
- (decision) Non-production policy checks begin advisory; after pilot tags, Terraform validity, and obvious secret exposure become blocking, followed within one or two sprints by staging gates for IAM wildcards, retention, alarms, and mutable images.
- (decision) SQS dead-letter queue support is deferred from MVP unless implementation proves trivial and does not complicate the module interface.
- (override) Repository quality and security rules override staged non-production timing: Terraform format and validation failures plus obvious secret exposure are blocking from MVP start; other non-production policy controls phase in after pilot.
- (change) Reconciliation adds explicit naming, optional minimal security-group creation, versions.tf evidence, Terraform artifact and provisioner hygiene, administrator-bypass controls, rollback recovery objectives, and observability incident measurement.
