# Epic 2 Retrospective: Run a Secure Scheduled Job in Non-Production

## Epic Review

Epic 2 completed all 10 planned stories. The epic established the full non-production scheduled-job control plane: reservation, least-privilege IAM, private ECS networking, task and log resources, CONFIG publication and validation, safe schedule activation, completion evidence, operations views, and controlled reruns.

Evidence reviewed included the completed story records, Story 2.10 review history, the architecture spine, project context, Terraform standards, repository validation, and sprint tracking.

## What Went Well

- Contract-first implementation kept identity, CONFIG, Deployment Identity, evidence, and compatibility rules explicit.
- Authority boundaries were consistently treated as design constraints: the Process Manager remained the occurrence/task writer and workload roles were separated from operator access.
- Security and reliability concerns were tested as negative cases, including IAM denial, duplicate delivery, stale bindings, ambiguous ECS outcomes, and rollback behavior.
- Documentation and rollback guidance were included with infrastructure and runtime changes.
- The final repository gate passed with Terraform validation, Ruff, mypy, tests, Checkov, and hygiene checks. The final run reported 242 tests, 227 subtests, and zero Checkov failures.

## Challenges and Growth Areas

- Boundary defects were often discovered during adversarial review rather than at first implementation: IAM leading-key scope, exact approval binding, idempotency conflicts, overlap locking, strict schema alignment, and approval expiry.
- Contract changes required coordinated fixture, manifest, release, and checksum updates; this created avoidable iteration when schema changes were made late.
- Validation diagnosis initially looked like a registry problem. The registry was reachable; the validator later exposed sequential formatting, lint, typing, and schema issues. Persistent-session execution and captured output made the failure stage clear.
- The project-lead retrospective input identified no additional qualitative highlights, so this record intentionally relies on repository evidence rather than inferred team sentiment.

## Key Lessons

1. Treat every authorization and idempotency boundary as a byte- and scope-level contract, not merely a successful API call.
2. Make concurrency protection transactional; read-before-write overlap checks are insufficient.
3. Update strict schemas and integrity metadata in the same change as the records they govern.
4. Keep credential-free validation diagnostics observable through stage labels, persistent execution, and explicit exit codes.
5. Preserve rollback, disable, and compensation behavior as first-class acceptance criteria.
